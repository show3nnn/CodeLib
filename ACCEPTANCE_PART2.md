# Приёмка часть 2 — каркас автоматической проверки

Версия 0.6.0 Alpha / build 20. Документ описывает **инструмент**, а не результат
внешней приёмки: снимки и замеры ниже — материал для человека, который проверяет
внешний вид, VoiceOver, Full Keyboard Access и полноэкранный режим.

## Запуск

```sh
bash scripts/acceptance.sh
```

Скрипт:

1. собирает **debug**-копию в `.build/acceptance/codelib.app`;
2. создаёт свежий каталог `.build/acceptance/run-<дата-время>/` c изолированным
   `data/` — пользовательский прогресс и `Application Support` не затрагиваются;
3. запускает приложение с `--acceptance-run <каталог снимков>`;
4. завершает процесс и печатает путь к отчёту.

Release-сборка `dist/codelib.app` не содержит этого режима: он включается только
под `#if DEBUG`. Отдельный скрипт намеренно не входит в `scripts/verify.sh`,
потому что создаёт окна, активирует приложение и снимает реальные пиксели.

Артефакты одного прогона:

| Файл | Содержимое |
|---|---|
| `screenshots/*.png` | 47 снимков экранов и состояний |
| `screenshots/SUMMARY.md` | таблица снимков, машинные наблюдения, чек-лист |
| `screenshots/report.json` | те же данные машинно-читаемо |
| `screenshots/accessibility-inventory.json` | AX-дерево по экранам |

## Что снимается

- Онбординг: приветствие в системной/светлой/тёмной теме, профиль, оформление,
  проверка среды.
- Главная, программа, учебный план, статистика, достижения — широкая светлая,
  широкая тёмная и компактная светлая.
- Баннер достижения в светлой и тёмной теме (в режиме Reduce Transparency, см.
  ограничения).
- Урок: широкая/компактная, светлая/тёмная, максимальный размер текста.
- Теория рядом с заданием и отдельный лист теории 470×620.
- Настройки: оформление, профиль, данные — обе темы и компактная ширина; история
  обновлений и «О codelib» — обе темы; редактирование профиля и баннер ошибки.
- Приветствие с Reduce Motion/Reduce Transparency (статичный ручной выбор).
- Полноэкранная главная и конец прокрутки редактора на 1000 строк.

Для каждого снимка записываются размер, тема, размер текста, число AX-узлов,
число интерактивных элементов без подписи и признак системного захвата.

## Машинные проверки

- **Accessibility-инвентарь.** Дерево снимается через AX-API **собственного**
  процесса (`AXUIElementCreateApplication(getpid())`,
  `AXUIElementCopyElementAtPosition`). Для каждого снимка отдельно сохраняются
  роли, подписи, значения, рамки и индексы родителей. Это не доказательство
  полноты или порядка обхода VoiceOver. Разрешение Accessibility
  не требуется и не запрашивается.
- **Подписи.** Считаются интерактивные элементы без `label/title/placeholder`
  и элементы нулевого размера; проверяются повторяющиеся подписи. Это эвристики,
  а не доказательство доступности; доступные роли перечислены в коде.
- **Key view.** Снимается текущая цепочка `initialFirstResponder` → `nextKeyView`
  с обнаружением цикла. Это только AppKit-хостинг: Tab-порядок SwiftUI-элементов
  зависит от Full Keyboard Access/VoiceOver и проверяется вручную.
- **Полный экран.** Один реальный вход с ожиданием анимации (до трёх попыток),
  снимок и выход с таймаутом; результат и время выхода попадают в отчёт.
- **Прокрутка.** 1000 строк черновика прокручиваются на 240 шагов с реальной
  перерисовкой `cacheDisplay`; считаются медиана, p95 и максимум шага, CPU и
  `phys_footprint`. Это синхронная перерисовка в тестовом процессе, **не FPS** и
  не покадровый профайл GPU.

Исторические замеры старых прогонов (числа зависят от машины):

- В старом прогоне получено 47 PNG, но AX-инвентарь для большинства снимков
  отсутствовал; утверждения о нуле дефектов на всех экранах отозваны.
- Прокрутка: медиана ≈6,9–8,2 мс, p95 ≈9,0–9,6 мс, максимум 11–24 мс; CPU
  ≈1,8–2,0 с; physical footprint после прокрутки 130–242 МиБ (не пик, метрика плавает между
  прогонами).
- Полный экран включился с первой попытки, снимок 1440×851; выход ≈0,04 с по
  метрике смены style mask.
- Цепочка key view: `HostingView → KeyViewProxy → PlatformViewHost → цикл`.

## Ограничения и почему это не приёмка

- **Нет разрешения записи экрана.** `CGPreflightScreenCaptureAccess()` = false,
  разрешение не запрашивается. Снимки сделаны `cacheDisplay` и композитом
  поверх фона выбранной темы. Обычные материалы и сайдбар при этом видны, но
  **чистое стекло** (`glassEffect`, панель приветствия, баннер достижения в
  обычном режиме) не растрируется и выглядит пустым. Баннер снят в варианте
  Reduce Transparency; стеклянный вариант нужно смотреть вручную с разрешением
  записи экрана.
- **Приложенный sheet** не растрируется тем же способом: лист теории снят тем же
  `TheorySheet` отдельным окном 470×620 без декораций листа.
- **VoiceOver.** Инвентарь показывает, что предлагается, но не проверяет речь,
  ротор, объявления и порядок обхода. Это делает человек.
- **Full Keyboard Access** — системная настройка. Прогон её не меняет; проверяется
  только текущая цепочка key view.
- **Reduce Motion/Transparency** — системные настройки. Явные значения передаются
  только тем представлениям, которые это поддерживают (`WelcomeCodePanel`,
  `AchievementBanner`); macOS не переключается.
- **Внешний вид** оценивает человек: снимок не является вердиктом.
- Отдельные компоненты (`FailureText`, баннер, приветствие, теория) и вторичные
  представления размещаются в искусственных окнах. Это не проверка их реального
  размещения и навигации в приложении.

Прогон активирует собственное приложение (`NSApp.activate`), чтобы AX-дерево
SwiftUI было доступно. Это действие уровня приложения, а не изменение системных
настроек и не запрос разрешений.

## Наблюдения для ручного прохода

- Имя профиля в сайдбаре обрезается: «Пилот приёмки» → «Пилот пр…». Решение
  (ширина, `lineLimit`, сокращение) не принималось в рамках приёмки.
- Панель приветствия и стеклянный баннер не попадают в снимки без разрешения
  записи экрана — проверить их вручную.
- Баннер достижения скрывается через 5 секунд; для ручной проверки его нужно
  вызвать реальным достижением или временно удержать.

## Чек-лист человека

Для каждого экрана из `SUMMARY.md`, в светлой и тёмной теме, широком и компактном
окне:

- [ ] Нет обрезанного или наложенного текста; переносы и крупный шрифт читаются.
- [ ] VoiceOver: заголовок экрана, назначение элементов, порядок обхода, действия;
      нет «пустых» кнопок.
- [ ] Full Keyboard Access: Tab/Shift-Tab достигают всех действий, фокус виден,
      порядок не сбивается.
- [ ] Fullscreen: макет не растягивается и не теряет боковую навигацию.
- [ ] Reduce Motion: приветствие и баннеры не анимируются бесконечно.
- [ ] Reduce Transparency: панели остаются читаемыми без стекла.
- [ ] Стеклянные поверхности (панель приветствия, баннер) выглядят корректно при
      разрешении записи экрана.

Только после этого прохода можно говорить о visual/VoiceOver-приёмке; текущий
каркас её не заменяет.
